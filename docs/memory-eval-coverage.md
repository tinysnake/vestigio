# Memory coverage: the 40-question annotation set

「记忆库覆盖了多少实际需要的历史信息」是提案 §4.8 的指标，也是整套评估里唯一
不能靠现有工具直接算出来的那一格：它需要一个**需求侧**的标注集——真实工作里发生
过的、需要依赖既有历史的提问，逐条判「答案在哪里」。

这份文档说明这批题从哪来、怎么标注、怎么复核，以及等有一份真实 store 之后覆盖率
怎么算。它**不**记录结果数字：数字由 `eval/memory/coverage.jsonl` 的字段算出来，
`coverage.mjs` 负责渲染，避免文档与数据各说一套。

## 1. 为什么难，以及这轮做到哪一步

其余指标都能从样本上算：Recall@K 看存储器里有没有那条记忆、Trigger 看 agent 有没有
发起查询、False Positive 看注入的东西对不对。覆盖率不行，因为分母是「真实发生过多少
次需要记忆的信息需求」，这个数只存在于历史会话里，而历史会话本身是原始数据，不是标注。

所以要先把分母造出来：从真实会话里挑问题，并标注每条问题的答案现实存在哪里。三类：

| 标签 | 含义 | 今天可核验吗 |
| --- | --- | --- |
| 库内 | 答案已经（或应当）作为一条长期记忆存在记忆库里 | 不能：本机没有生产 store |
| 仅历史 | 答案只存在于原始会话记录里，没有任何一条记忆承载它 | 能：在 Obelisk 里查得到 |
| 缺失 | 任何地方都没有记录，当时只能重新推导 | 能：查不到即判 |

覆盖率 = 库内 / (库内 + 仅历史 + 缺失)，分母只算 `durable` 的行（见 §3）。本机没有
store，所以现在能给出的只有分母和「仅历史/缺失」的切分；库内一列等有 store 后再填。

## 2. 题目从哪来

- 来源：本机 Obelisk 索引里 `<repo>` 相关项目的真实会话（61 个会话，约 2.5 万条消息，
  2026-11-17 至 11-20），每条题都带 `session_id` 与 `message_uuid`，可以回溯原文。
- 抽法：取用户消息（`role='user'`、非 meta、非 sub-agent 派发模板），长度 20–400 字，
  再人工挑出「回答它需要项目既有的决定/约定/事实」的那些。**没有**用「上次」「之前」
  这类关键词筛：真实的回忆需求大多没有标记，而带标记的消息里有一半是「刚才你说的是
  什么意思」这种会话内指代，反而与长期记忆无关。
- 取舍：35 条覆盖 2026-11-17 到 11-20 的设计与实现讨论（短期/中期记忆、注入预算、
  模型选择、stale 语义、主动写入、后台 repair、中文检索、上游 PR）。
  题面保留用户原话，不改写——改写会引入出题人的答案。

## 3. 字段与两条轴

`coverage.jsonl` 每行一条：

| 字段 | 含义 |
| --- | --- |
| `id` | `cov-NN` |
| `question` | 用户原话（去空白），英文与代码片段照抄 |
| `asked_at` / `session_id` / `message_uuid` | 提问锚点，可回溯 |
| `topic` | 一句话主题，便于按主题分组看覆盖率 |
| `draft_answer` | 出题人写的答案（一行） |
| `verified_answer` | 一审/终审核对后改正的答案；没有这一项就说明初判答案被确认无误 |
| `draft_durable` / `draft_answer_lives` | 出题人的初判，保留用于对比 |
| `durable` | **一审结论**：这条答案是不是长期记忆该持有的知识 |
| `answer_lives` | **一审结论**：`history` / `nowhere` / `unverified` |
| `evidence` | `{session_id, message_uuid, quote}` 列表，答案的原文出处 |
| `judge` | 谁做的这一审（`gpt-6` / 用户名） |
| `notes` | 与初判不一致时的一句话理由 |

两条轴必须分开，因为它们回答不同的问题：

- `durable=false` 的行（如「刚才你说的是什么意思」「效果够好了吗」）测的是会话内
  连续性，不是长期记忆。把它们算进覆盖率会让分母被闲聊稀释。
- `answer_lives` 测的是**记录现实**，不是应然。一条 `durable` 但 `nowhere` 的行说明
  当时讨论出的结论从未落盘——这正是「缺失」要暴露的东西。

## 4. 复核流程

1. 出题人（我）从真实会话抽题、写 `draft_answer` 与初判。
2. 一审（GPT-6）用 Obelisk 逐条核对：答案是否真在历史里、在哪条消息、`durable` 是否
   成立。分歧写进 `notes`，`draft_*` 字段保持原样。
3. 终审（你）：看 `question` 与 `draft_answer` 是否事实正确，看两条轴的结论是否同意。
   复核表由 `node ./coverage.mjs --out out/coverage.md` 生成。
4. 分歧行改完再写回 `coverage.jsonl`，`judge` 记为终审者。

不做的事：不让评估模型自己出题（会偏向它能答的题），不因为某条题「不好答」而删除
（那正是覆盖率要暴露的部分），不改写用户原话。

## 5. 第一轮的结果

一审（GPT-6，0 条 `unverified`）判了 40 条；终审时撤掉 5 条「判成哪边都说得通」的题
（`cov-09/13/23/35/39`），保留 35 条。编号保留空位，早先的引用仍能对上。

- **30 / 35 条属于 `durable`**：另外 5 条是会话内指代（「刚才你说的是什么意思」）、
  一次性方案与运行细节（live 测试怎么跑、某次验证用了什么端点、某个上游 PR 的语气怎么读）。
- **30 条 `durable` 全部是 `answer_lives = history`，`nowhere` 为 0**：这批题里没有
  「讨论过但哪儿都没落盘」的情况，也没有一条已经作为长期记忆存在。所以覆盖率的
  **分母是 30、分子是空的**（本机没有 store）；现在算出来的 0% 是设备缺失导致的空真，
  不是质量结论。
- 一审与初判有 **2 处分歧**（`cov-10`、`cov-38`），并改正了 **8 条初判答案**
  （`cov-06/07/10/22/26/28/29/38`）。值得记下的一处：`cov-28` 我原本以为 150s/300s
  是测试 run 的死线，实际是产品侧修复的限制（单次尝试 150s、一次 `agent_end` 通过
  300s）。更正留在 `notes` 与 `verified_answer` 里，`draft_*` 不动。
- 证据不是模型复述：60 条 `quote` 全部用 `message_uuid` 回查原文，逐条核对为逐字子串
  （0 条缺失、0 条不符）。

撤题本身有代价，要一起读：撤掉的是判不清的那 5 条，样本因此偏向「判得清」的题，
覆盖率会比真实情况显得更确定——它不影响分母的量级，但会让标注一致率偏高。35 条、
单人、单项目、偏设计决策类，仍然只够说明「这批需求确实只在历史里」，不够说明
生产记忆库的覆盖率是多少。

## 6. 等有 store 之后怎么算

0. 先用 `node ./coverage-store.mjs --store <real store> --project <abs path> --out out/coverage-store.json` 拿读数覆盖率。它先复制 store（含 `-wal`/`-shm`）到临时目录，再把每条 durable 问题的原文交给 `vestigio search`，记录是否返回任何卡片，并按状态计数；CLI 会以读写方式打开 store 并跑迁移，复制是避免碰到原库的唯一办法。这一层不需要 `expected_memory_ids`：它回答「库能不能对这个问题给出任何东西」。当前对两份 harness store 都是 30 条 durable 题、0 条返回卡片，说明命令能跑通，生产数字仍待真 store。
1. 用 `node ./audit.mjs --store <real store> --cases coverage.jsonl` 得到「预期记忆
   id 在 store 里是否存在」的那一半；当前 `coverage.jsonl` 没有 `expected_memory_ids`
   字段，因为本机没有 store，凭空的 id 只会制造假数据。等 store 存在后再按题意补。
2. 补字段时只标「这条问题的答案应该由哪条记忆承载」，不标「现在是否相似」——相似度
   是检索指标（Recall@K）的事，覆盖率只问存不存在。
3. 覆盖率的分子只算 `durable=true` 且 `answer_lives != "nowhere"` 且 store 里确有其
   内容同义行的题；分母是 `durable=true` 的全部行。`nowhere` 的行永远进不了分子，
   它们是需要补写记忆的入口清单。

## 7. 已知边界

- n=35，单人单项目，且都是「设计与决策」类问题；日常改动类问题（「这个函数谁写的」）
  没有抽，覆盖率会因此偏高或偏低都说不准——样本量到 100+ 之前不下结论。
- `asked_at` 是提问时刻，不是答案形成的时刻；两者可能相差几个会话。实测把 35 条
  的 `evidence[].message_uuid` 逐个取回时间戳后，**没有一条证据早于 `asked_at`**
  （全部等于或晚于提问时刻，多数是同一会话里几分钟后的回答）。这条边界比原先写的更
  强：这 35 条记录的是「会话中现场产出的知识」，不是「从更早历史里召回的需求」。
  因此它作为**写入侧**分母是有效的（30 条 durable 事实目前只存在于原始历史，没有一
  条进了记忆库），但不能当召回测试集用——典型召回形态（问题在后来，答案早已定下）
  在这批里恰好没有出现，因为这种问题很少以自由文本的形式写出来。
- 由此也否掉了一个探针设计：用问题里的词片（n-gram 切片）做 `LIKE` 扫描去找「回答
  那句话所在的会话」——35 条里 34 条「找到」，但那是问题自己的消息被同一张 `messages`
  表命中，属于循环论证。要做召回侧测量，必须先按「证据早于提问」筛样本，再让改写步
  骤（模型给出 1–3 个短索引词）去命中，而不是直接拿问题原文的切片当检索词。
- `answer_lives` 的判定依赖 Obelisk 索引完整性：没被索引的会话等价于「从没记录」。
- 「仅历史」不等于「应当写入记忆」：有些结论只在当时有效，过期即废；`durable` 轴
  就是为了把这类排除掉。
