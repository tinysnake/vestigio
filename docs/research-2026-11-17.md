## Obelisk 文档与本机实现存在能力差异

已读取上游 [README](https://github.com/tommy0103/obelisk/blob/main/README.md) 和 [API reference](https://github.com/tommy0103/obelisk/blob/main/skill-doc/references/api-reference.md)。`main` 链接是移动目标，正式实现应固定验证过的发行物或提交。

上游 API 文档提供以下能力。

- `search(text, opts?)` 使用 FTS5，支持来源、项目、时间、失效记录及返回范围选项。
- `messages(optsOrUuid)` 支持单条消息、有限时间窗口、父路径和 Session 分页。
- `messages({ around: uuid, relation: 'parents', beforeCount: 3 })` 按父链读取。默认时间邻居不代表同一因果分支。
- `includeInactive` 默认关闭。隐藏记录不会因开启该选项而显示。
- `sql(query, ...params)` 是参数化只读查询入口。

本机代码证据为 `/opt/homebrew/lib/node_modules/@obelisk-apps/cli/dist/core/src/query.js`。

本机 `search` 读取的选项是 `limit`、`sessionId`、`project`、`after`、`before`、`cwd`、`source`、`includeMeta`、`includeInactive` 和 `fallback`。尚未读取上游文档中的 `projectPath`、`snippetTokens` 或 `contextLimit`。

因此，仅传入这些新选项可能被静默忽略。特别是 `projectPath` 被忽略时，会破坏项目检索范围。`project` 和 `cwd` 在本机实现里使用 SQL LIKE，不能直接当作永久项目身份或精确路径过滤。

本机已经实现 `messages` 的有界定位方式与父路径选项校验。但本轮只检查实现，没有用合成 Obelisk 索引执行完整端到端查询，也没有验证 UUID 在重建、移动文件后的稳定性。PR-03 负责补足这些验证。

本机查询入口 `/opt/homebrew/lib/node_modules/@obelisk-apps/cli/dist/core/src/core.js` 的 `executeQuery(scriptContent, invocation)` 先调用 `refreshQueryIndex()`，再打开只读数据库执行查询。因此，“查询 API 不修改历史内容”不等于“CLI 调用不发生索引维护”。是否等待 writer、如何限制刷新耗时和如何报告陈旧索引，仍需真实运行验证。

本机 Obelisk 源文件声明 `AGPL-3.0-only`。计划采用外部 CLI 适配，发行前记录依赖与分发方式，不直接复制内部实现。

## pi 有可用的接入钩子

本机依据为 `/Users/snake/.pi/agent/install/releases/1.5.2/node_modules/@earendil-works/pi-coding-agent/docs/extensions.md`。

- `session_start` 可初始化本地状态，不代表需要向模型注入词表。
- `input` 事件读取原始输入，来源包括 interactive、rpc 和 extension，可返回 transform 修改文本。它位于扩展命令处理之后、skill 与模板展开之前。
- 排队和中断输入通过 `streamingBehavior` 区分 steer 与 followUp。实际提交位置、失败重试与去重需要真实运行验证。
- `before_agent_start` 在输入展开后触发，可返回附加消息。它不直接等价于修改用户输入末尾，不能未经验证就用独立消息替代最新要求。
- `pi.registerTool()` 可注册模型可调用工具。
- 文档说明，强制替换整个 system prompt 会改变前导系统提示。最新需求已经排除热点词表与动态短摘要进入 system prompt。
- Session 切换、分叉、回退、压缩和继续需要维护相应注入记录。

这是文档与包检查结论。本轮没有加载 pi extension，没有向主 Agent 注入热点，也没有测 Prompt Cache 命中情况。

## 中文与短词匹配原型

原型位于 [lexical_probe.py](probes/lexical_probe.py)。它是临时验证工具，不是生产检索模块。

实际执行命令为 `python3 /tmp/vestigio-plan-probes-20261117/lexical_probe.py`。仓库中的文件保存相同内容，便于复现。脚本使用内存数据库，不读取真实对话。

合成文本为 `一二期服务器部署配置，pi-agent 使用 memory.search。`。

| 查询 | 默认 FTS5 | trigram FTS5 | 规范化子串对照 |
| --- | --- | --- | --- |
| 服务器 | 未命中 | 命中 | 命中 |
| 配置 | 未命中 | 未命中 | 命中 |
| pi | 命中 | 未命中 | 命中 |
| pi-agent | 命中 | 命中 | 命中 |

结论只针对这个合成输入。

- 默认 FTS5 不能直接解决连续中文文本中的所有子词匹配。
- trigram 可覆盖长于两个字符的子串，但全文查询不匹配不足三个 Unicode 字符的子串。
- 子串匹配适合小热点池的候选提醒，但不能证明语义相关，也可能误命中。
- 中期检索需要比较分词索引、别名及短词补充，不能以这张表推导总体召回率。

已通过 Context7 查询 [SQLite FTS5 官方说明](https://www.sqlite.org/fts5.html)，确认 trigram 的短子串限制和 BM25 排序方向。FTS5 内置 `bm25()` 的较小值排在前面，不能把分数当作答案置信度。

## 尚未证明的假设

- 主 Agent 在新规则和热点提醒下会主动查询，且不会过度查询。
- 不超过 200 字符的二次导航摘要能准确说明 500 至 1000 字中期摘要的内容范围与适用问题。
- 同一 Session 不重复注入的策略在压缩与记忆修订后仍能保持足够的可发现性。
- 本地约 0.8B 模型能够处理证据筛选和历史冲突。
- 复杂检索约 30 秒可同时满足交互与准确性要求。
- Obelisk 成功检索后必须总结并保存，同一摘要返回主 Agent，再派生短摘要。该闭环能否在真实使用中摊薄后续召回成本仍待验证；中期总结和写入增加的本次耗时必须计入。
- 命中次数、访问次数和上次访问时间能够改善排序与归档，且不会使低频重要记忆退出默认检索。

这些假设需要计划中的真实运行与对照实验，不能用文档检查或合成匹配结果替代。
