# 需求修订记录

本记录补充 2026-11-17 的原始需求与第一份开发计划，包括输入注入、两级摘要、访问统计，以及后续关于热点更替、模型检索和检索后强制形成记忆的讨论。与 [原始需求](requirements-2026-11-17.md) 不一致时，以本记录为准。原始附件保持原样，便于追踪设计变化。

## 1. 热点只在本地匹配，命中后追加到用户输入末尾

- 短期热点关键词不注入 system prompt。
- Session 初始化只在宿主程序本地准备关键词和别名索引，不向模型发送整份词表。
- 每轮真实用户输入均进行本地匹配，不调用 LLM。
- 命中后，在该轮输入的提示词末尾追加相关记忆短摘要和中期长摘要的获取方式。
- 获取方式应包含稳定 URI 与实际注册工具的读取语法。
- 不自动注入完整长摘要，也不重复注入已提供的记忆块。

输入示意如下。

```text
用户本轮的原始请求

<matched_memory>
记忆 ID 与标题
短摘要：这条记忆包含什么，什么时候值得读取。
长摘要：memory://<store-id>/<memory-id>
读取方式：调用 memory_read，传入上面的 URI。
</matched_memory>
```

这只是布局示意，不是最终工具参数契约。附加块必须明确属于检索参考资料，不能把历史内容包装成用户指令。

去重规则尚未逐项由使用者定义，计划先采用以下默认解释。

- 同轮多词或别名关联同一记忆，只追加一份。
- 同一 Session 内同记忆只注入一次，重启或继续 Session 保留记录。
- 新 Session 可再次提供。分叉只继承当前分支中的已注入记录，回退不受被放弃分支影响。
- 修订更新与上下文压缩不自动触发再次注入，是否允许需另定规则。
- 只将实际交付的块记为已注入。发送失败或预算未容纳的条目仍可后续提供。

热点匹配再次命中可以更新统计，但不必重复展示。统计和提示去重是两种行为。

## 2. 摘要生成有明确的两级依赖

| 层级 | 内容依据 | 长度 | 应回答的问题 |
| --- | --- | --- | --- |
| 中期长摘要 | Agent 检索得到的 Obelisk 历史证据 | 500 至 1000 字 | 我们之前讨论了什么，得出了什么结论？ |
| 短期导航摘要 | 对已完成中期长摘要的二次总结 | 不超过 200 字符 | 这条记忆包含哪些信息，什么时候值得读取？ |

中期摘要保留讨论背景、结论、决策依据、必要条件、未解决问题和冲突。附带可定位来源，不机械选择最新时间戳作为唯一正确结论。

短摘要用于判断是否值得读取长摘要，不要求覆盖全部事实。它应指向具体的中期记忆 revision，不能独立从原始 Session 生成后与中期内容失配。

实现上先校验并保存中期正文、来源及待生成短摘要任务，将同一正文返回主 Agent，再生成短摘要。中期版本可独立读取，不必等短摘要完成。第二阶段失败只重试第二阶段。短摘要必须绑定正文 revision，未完成导航的版本不进入热点；更新正文时不能留下指向新正文的旧导航。

中期暂按正文非空白 Unicode 字符数校验，短期按完整导航文本的 Unicode 字符总数校验，包含标点与空白。标题、来源列表与 URI 不计入摘要本身。这是计数约定的建议。证据不足时不为达到 500 字填充推测。

旧计划中“一次提炼同时生成全部摘要”的安排撤销。两阶段模型调用、Token 与费用分别记录。具体模型仍未选定。

## 3. 命中、访问与时间参与排序归档

每条中期记忆至少记录以下字段。

| 字段 | 意义 | 初始口径 |
| --- | --- | --- |
| hit_count | 命中次数 | 被热点匹配选中，或作为搜索候选返回。保留来源 channel，合计去重 |
| access_count | 访问次数 | 完整中期摘要成功读取并交付给调用方 |
| last_access_at | 上次访问时间 | 最近一次成功前台长摘要读取的时间，未访问时为 null |

以上字段由使用者明确要求。“命中”是否同时包含热点和搜索，以及具体事件去重粒度，仍是计划建议。短摘要注入、卡片展示和后台维护读取不计为长摘要访问。

排序先考虑当前问题相关性，再以热度和最近访问作为有界辅助信号。不能让历史热门条目不断积累曝光，挤走当前真正相关的条目。

归档综合时间、命中、访问与保护规则。高命中低访问不直接意味着无价值，低命中也不直接意味着过时。第一版不强制主 Agent 额外发送实际采用反馈；访问不能在报告中冒充最终任务采用。

归档命中不直接恢复 Active。成功访问更新统计并进入恢复评估，默认仍保留可审阅的维护流程。

## 6. 热点更替补充

使用者明确不希望设置固定 48 小时等硬失效时间，避免项目闲置几天后短期热点全部消失，并希望结合时间和容量考虑更替。

开发计划提出以下方案，细节属于建议，尚未经过实际回放验证。

- 按项目持久化热点池，项目闲置不清空，其他项目的活动不使本项目热点衰减。
- 容量限制记忆条数、别名总数与索引字节。每轮注入预算另行限制。
- 初版用项目真实用户输入轮次表示活跃时间，没有输入就不推进。最近命中、最近读取和近期频率影响留存优先级。
- 达到容量上限且出现更有价值的候选时才替换。未满时不单凭时间流逝逐出有效热点。
- 热点退出只影响自动提醒，中期摘要、短摘要与 URI 均保留，不等于中期归档或删除。
- 通过主动检索成功读取、生成新的完整摘要或显式固定，均可产生入池候选。候选搜索曝光本身不推动入池。
- 项目恢复时加载旧快照，热点移出再入不重置 Session 注入去重记录。

容量、权重、活跃轮次衰减、新条目试用和替换余量留待实验。中期归档也不能绕过这些保护，仅因项目闲置就整体移走仍有效的热点。

## 7. 模型分层检索的安排

计划原有 PR-06 已包含独立记忆检索执行流程，PR-09 已安排本地约 0.8B 与低成本付费模型的比较。因此本轮无需额外搜索聊天历史以确认是否遗漏该项。

现在进一步明确模型执行器负责 Active 摘要、Archived 摘要和 Obelisk 原始证据的逐层探索与停止判断。基础索引先生成候选，模型选择并读取摘要，证据不足再向下搜索，足够就停止。它不介入每轮热点词匹配。

第一版配置一个本地或付费后端，不自动从本地升级到付费，也不要求搜索与两级摘要生成采用同一个模型。检索与两级总结分别记录费用，检索和中期总结共用本次请求总预算；短摘要任务另记完成时间。约 0.8B 能否胜任、付费模型是否更划算仍未验证，候选规格不代表最终选型。

## 8. Obelisk 检索必须同时形成记忆

使用者明确要求，LLM 必须通过 Obelisk 查历史时，必须完成一次中期摘要。同一份摘要既返回主 Agent，又保存到记忆系统，再据此更新短期记忆。它是成功检索流程的一部分，不经过额外的可选保留价值判断，也不要求主 Agent 再调用保存工具。

正常路径为 Obelisk 证据检索 → 中期摘要生成与校验 → 持久化正文、来源和短摘要任务 → 返回同一摘要及 URI → 二次生成短摘要、关键词与别名 → 按既定规则更新热点池。短摘要可随后执行，不阻塞已保存中期正文的返回。

无结果、有效证据不足或检索取消时，不能为满足流程而编造摘要。存在分歧时保留冲突和未决问题。已有中期摘要足够时直接复用，不必下探或重复生成。

同一请求与同一来源版本的重复执行应复用已完成结果，不重复建记忆。保存失败必须与查询结果分开报告，不能声称已保存或已更新热点。短摘要失败保留中期记忆并可恢复重试。中期生成与写入计入本次请求耗时，短摘要更新完成时间另记。

首次形成的中期摘要成功交付主 Agent 时，也按既有访问口径记录一次 access；保存与后台短摘要生成本身不增加访问次数。重试交付通过事件 ID 去重。
