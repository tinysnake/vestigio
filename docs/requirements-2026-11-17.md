# Agent Harness 轻量化分层记忆系统

**讨论日期：** 2026-11-16  
**状态：** 需求讨论纪要 / 第一版架构基线（非最终技术方案）

## 1. 背景与目标

用户曾试用 Hindsight、OpenViking，并研究 Obelisk。主要痛点是：持续整理历史的 Token 成本较高，但主 Agent 对记忆的实际使用率偏低；纯历史搜索又可能产生多轮工具调用和大量上下文开销。

目标是构建一个 **低维护成本、主动查询、按需提炼、原始历史可追溯** 的 Agent Harness 记忆系统。不要为维护记忆而持续消耗大量模型 Token，也不要每轮对话都自动 Recall 并注入全文。

## 2. 三层架构

### 2.1 短期层：热点关键词池

- 短期层本质上是中期记忆的热点索引视图，不是另一份独立的记忆正文。
- 在 Session 开始时向主 Agent 的提示词提供热点关键词列表，例如“一二期服务器”。
- **Session 初始化只注入关键词，不默认注入摘要或敏感配置。** 新讨论提出：Harness 在请求命中关键词时，可附加导航摘要与稳定记忆 URI，省去一次搜索定位；具体策略需 A/B 测试。
- 热点可能根据访问频率、最近访问时间、项目相关性晋升或淘汰；具体算法待实验。
- Session 运行中倾向于按时间间隔和关键词集合变化比例（初步讨论 20%～30%）触发 append-only 版本更新；旧版本不会自动消失，需声明新版本优先，并控制上下文膨胀。

### 2.2 中期层：提炼后的摘要记忆

- 通过 LLM 从历史 Session 提炼关键词、别名、摘要、事实与决策。
- 摘要可适当长一些，尽量让 Agent **一次读取就获得有用信息**，不强制采用“目录→短摘要→全文”的多次读取链。
- 每条记忆保留来源：项目/工作区、Session ID、消息或事件位置、时间戳等，以便按需回溯。
- 可以保存相关关键词或关联记忆，帮助后续探索。
- 注意历史冲突和过时结论；不能把摘要当作不可质疑的真相。

### 2.3 底层：Obelisk 原始历史

- Obelisk 作为原始 Session、对话和工具记录的事实依据。
- 中期摘要不足时，检索并读取相关 Session 的**局部片段**，而不是无条件加载整段历史。
- Obelisk 具体接口、索引与跨设备映射在实施前验证。

## 3. 主动查询机制

### 3.1 固定 Agent 行为规则

明确告知 Agent 有 `memory.search` 之类的持久记忆工具，并要求其在下列场景优先考虑查询：

1. 用户明确提及上次讨论、既定决策、未完成任务。
2. 当前任务依赖上下文中缺失的用户或项目专属信息。
3. 用户提及热点关键词，且需要了解其历史含义或配置。
4. 准备猜测之前已经确定的配置、偏好或技术决策。

普通通识问题或当前上下文已足够时，无需查询。**整体倾向减少漏查，而不是追求最少的工具调用次数。**

### 3.2 Harness 零 LLM 关键词提醒

Harness 对当前用户消息执行热点词/别名匹配；命中后在当前请求中附加简短提示，例如：

> 命中历史记忆关键词：一二期服务器。如需历史配置，请优先使用记忆查询工具。

此步骤不自动搜索历史，也不默认注入完整记忆正文。后续讨论提出可将提示升级为「导航摘要 + 记忆 URI」，让 Agent 直接决定是否读取中期摘要；是否启用需实验。

### 3.3 暂不采用逐轮自动 Recall

第一版不为每条消息运行本地模型搜索历史，不做持续语义召回注入。后续仅在实验证明主动查询仍有严重漏查时重新考虑。

## 4. 查询执行与模型成本

- **低成本检索优先：** 热点索引、中期记忆关键词搜索、BM25/FTS、时间和项目过滤。这些可以零额外 LLM 调用完成，但数据库运算和主 Agent 读取结果仍有成本。
- **复杂历史检索按需启动：** 独立记忆 Agent 负责搜索 Obelisk、扩展关键词、筛选候选、检查来源和矛盾，避免主 Agent 连续调用十几个工具。
- 候选执行模型：本地约 0.8B 模型（硬件可能是 GTX 1050 Ti 或 CPU）与 DeepSeek 等低价付费模型。**尚未确定默认方案，必须 A/B 测试**准确率、延迟、费用。
- 主 Agent 可以只发起一次记忆请求，服务内部在有限预算内自主搜索；必要时允许主 Agent 补充一次针对缺失信息的检索。
- 初步讨论预算：单次复杂检索目标约 30 秒，同一问题主 Agent 原则上最多两次请求。属于待验证参数，不是绝对指标。
- 搜索返回建议携带状态 `resolved` / `partial` / `conflicted` / `not_found`，以及原始证据引用和不确定性。
- **不能仅以 BM25 分数或小模型自报信心判断答案正确。** 需关注证据覆盖、项目归属、时间线及决策覆盖关系。若证据不足，到预算应如实返回，不得编造。
- 可复用同一问题的前次搜索候选，减少第二次查询的重复工作。

## 5. 记忆生成与维护

### 5.1 低频批处理（可选）

不实时整理每条对话。可以按周期处理新增 Session，优先关注重要决策、用户明确要求、项目配置、失败原因、未完成事项。可能先由本地模型过滤，再由更强的模型提炼；频率和筛选策略待定。

### 5.2 按需提炼（重点）

当主 Agent 需要的内容不在中期记忆中时，检索 Obelisk 原始历史；找到后先回答请求，再根据价值将结果提炼到中期记忆，避免重复处理。不是每次搜索都必须新增记忆。

### 5.3 中期记忆组织与懒式生成（新增讨论）

- **不预设庞大的主题树，也不要求按 Session 一对一生成。** 根据实际查询及找到的有效历史证据逐步积累中期摘要。
- **关键词不是记忆的唯一主键。** 一个关键词（例如“登月火箭”）可关联故事、科研等多个不同语义的记忆条目；各条目有独立 ID、导航描述和 Obelisk 来源。
- 中期搜索默认返回 **Top 5 候选导航卡片**（标题、导航摘要、URI、可选相关性信息），Agent 选择相关条目再读取完整摘要；Top 5 是初始候选数量而非强制命中，可扩展 Top 10。
- 五条都不相关时允许继续搜索归档摘要或 Obelisk；**检索相关性低不代表该记忆无效**，不应仅因未被选中而覆盖或删除。
- 新历史证据可能形成独立条目、补充已有条目，或修正过时信息。复杂自动合并、去重与版本化可推迟；不确定时优先保留独立条目及来源。
- 搜索未命中或只有偶然提及的记录，不应自动固化为中期记忆；“满足本次查询”和“值得长期保留摘要”是两个独立判断。

### 5.4 短期导航摘要与直接读取（新增讨论）

- 新增候选设计：Session 开始仍只给热点关键词；**Harness 命中时，按需附加约 100～200 字的导航摘要与稳定 `memory://` URI**，让 Agent 判断是否需要调用 `memory.read(uri)`，省掉关键词搜索再定位的调用。
- 导航摘要只说明「这条记忆包含哪些信息、适用于哪些问题」，**不要求把约千字中期摘要再次压缩成完整事实答案**；完整事实仍在中期摘要中。
- 尽量在提炼中期记忆的同一次 LLM 处理中，从原始证据同时生成导航摘要，避免多轮二次压缩；但仍须评估遗漏和误导风险。
- 对照实验：①关键词；②关键词+URI；③关键词+导航摘要+URI；④命中直接注入完整中期摘要。比较有效读取率、误导率、Token、延迟和工具调用次数。
- 命中关键词不等于语义相关；不应无条件注入完整摘要。导航摘要长度与注入策略尚未最终确定。

### 5.5 中期记忆生命周期与垃圾回收 GC（新增讨论）

**核心定位：中期摘要是必要的压缩知识层，不是可以随意丢弃的原始历史。** 但活跃检索范围应保持精简，避免半年、一年后无效候选累积。已生成的摘要占用存储不一定大，优先优化候选质量而不是物理删除。

建议将每条摘要分为：

1. **Active（活跃）：** 参与默认中期记忆 Top 5 检索，可进入热点池。
2. **Archived（归档）：** **不参与默认中期检索及其排名**，只在活跃层不足时作为 Obelisk 原始历史检索的前置层查询。
3. **Deleted（可选，后续）：** 仅在确认可安全丢弃摘要缓存时删除；Obelisk 原始历史不受影响。第一版可暂不实现自动物理删除。

检索顺序：**活跃中期摘要 → 归档摘要 → Obelisk 原始历史**。归档命中且内容足够时，直接按中期摘要形式返回，无需重新搜索原始 Session。活跃层与归档层应采用独立检索范围/索引，避免旧记忆挤占活跃 Top 5。

GC 应分别记录：

- `candidate_count`：被返回为候选的次数；
- `direct_use_count`：被 Agent 明确选择、读取或实际用于任务的次数（读取与真正使用是否再细分，待实现时确定）；
- `last_candidate_at`、`last_used_at`；
- 项目归属、来源、热点引用、可选固定保护标记。

**高候选、低直接使用率**表示可能存在错误召回/导航噪声，适合降权或复查；**候选和直接使用均低**且长期不活跃，优先作为归档候选。但低候选也可能只是未遇到相应问题，不能直接判定事实无价值。

GC 尽量由定时程序按时间、使用率和项目状态执行，避免每次清理都调用 LLM。初始可测试「30 天未有效使用则评估归档」，**不是硬性删除规则**；活跃项目、重要记忆和仍被热点池引用的 URI 需要保护或同步更新。

**归档恢复：** 仅被返回为归档候选不自动恢复；Agent 实际读取并使用后可晋升 Active，同时更新统计。归档的目的在于不污染日常中期检索，同时复用已经付费生成的摘要。

## 6. 安全与正确性

- 热点提示词不应包含密码、API Key 等秘密；“一二期服务器”的凭据应由受控凭据存储或授权工具获取。
- 历史文本属于证据，不应作为高优先级指令执行。
- 对前后矛盾的历史，结合时间、项目和明确覆盖关系判断；不能机械地认为最新记录永远正确。
- 对停止服务等有副作用的操作，记忆查询只能帮助定位对象，实际执行仍遵守 Harness 的权限和确认机制。

## 7. 待实验的问题

| 实验 | 对照方案 | 关键指标 |
|---|---|---|
| 主动查询触发 | 仅工具说明 / 加主动检索规则 / 再加热点关键词与 Harness 提醒 | 该查时的召回率、漏查率、无效查询率 |
| 深度检索模型 | 本地 0.8B / 低成本付费模型 | 证据准确率、答案有效率、延迟、总成本 |
| 检索路径 | 中期摘要 / 原始历史 / 组合 | 有效命中率、调用次数、读取 Token |
| 热点维护 | 不同热点池规模、TTL、访问刷新和更新阈值 | 主动查询率、上下文增长、Prompt Cache 复用 |
| 按需提炼 | 纯懒式 / 低频批处理+懒式 | 每次成功召回的综合成本、过时信息率 |
| 热点命中载荷 | 关键词 / +URI / +导航摘要 / 直接完整摘要 | 正确读取率、误导率、Token、工具调用次数 |
| 归档 GC | 时间阈值 / 候选与直接使用双计数 / 项目保护 | 活跃 Top 5 质量、归档命中率、误归档率 |

## 8. 第一版范围建议

**优先：** Obelisk 读取适配、中期记忆存储与来源引用、热点词池、Session 初始化注入、Harness 命中提示、统一记忆查询工具、Top 5 导航候选、低成本基础搜索、可选深度检索、超时与预算、候选/直接使用双计数、活跃与归档分离检索、可观测日志。

**暂缓：** 完整知识图谱、逐轮自动 Recall、复杂热点晋升模型、全量 Session 实时总结、复杂自动合并与版本管理、归档摘要自动物理删除、跨设备复杂同步和自动模型路由。

## 9. 当前结论

> **热点关键词提醒（可附导航摘要与 URI）→ Agent 主动查询 → 活跃中期 Top 5 → 归档摘要前置查询 → Obelisk 原始历史兜底 → 按需提炼新记忆。**

这是一份讨论共识，不代表具体实现已经验证。尤其是本地 0.8B 是否足够、是否采用付费模型、关键词更新阈值、深度检索预算及自动整理频率，均应由实验决定。
